# Module Tool Scaffolds

`init-module/` mirrors the module tree generated by `module:init`.

- Files ending in `.tmpl` are rendered as UTF-8 text and written without the suffix.
- Other files are copied byte-for-byte.
- Tokens may appear in template contents or paths. Supported tokens are:
  `%SYSTEM_ID%`, `%SYSTEM_NAME%`, `%CLASS_PREFIX%`, `%MANAGED_TSCONFIG%`,
  and `%CORE_REF%`.
- Rendering fails when a `%TOKEN%` placeholder remains unresolved.

Keep SDK examples current here. `module-init-scaffold.test.ts` generates the tree and runs
`module:check` against it.

The standalone release helper, test suite, npm commands and release guide are
copied byte-for-byte. Only the module-specific workflow filenames/IDs/pins and
initial README/changelog use templates. Keep the distributed helper/test copies
in maintained modules aligned; there is no runtime import from the Core tree.
The scaffold regression executes the generated helper tests and verifies the
tag-validation/manual-publication workflow boundary.

The artifact handoff and publisher scripts/tests are also copied. The standalone
publisher uses CI's archive bytes and bundled pinned-Core history generator;
it does not install dependencies or invoke module packaging. Keep these copies
aligned with the maintained modules and Core's artifact handoff tests.

`ci-reuse.mjs` and its tests also ship unchanged. They compare complete Git trees
for the narrow version/changelog exception; source/config/dependency changes
require full validation. Version-bearing module metadata still invokes the pinned
packager. Keep workflow conditions and these scripts together when updating the
scaffold or an existing module. See Core ADR-0066's October21 addendum.
