# ADR-0035: Public Manifest Module Distribution

**Status:** Accepted - Implemented
**Date:** September 7, 2026
**Supersedes:** None
**Revises:** ADR-0007 (public unauthenticated sources and fail-closed host governance), ADR-0033 (bounded activation of remote module distribution)
**Related:** ADR-0003, ADR-0004, ADR-0006, ADR-0008, ADR-0027, ADR-0029

---

## Context

Sheet Delver currently supports two runtime module locations:

- `<DATA_DIR>/local/modules` for development source
- `<DATA_DIR>/modules` for managed production artifacts

The manager, lifecycle records, compatibility resolver, trust policy,
permission-escalation review, dry-run evaluation, and artifact records already
exist. Source profiles, an index model, and remote-fetch scaffolding also exist,
but ADR-0033 deliberately made every network-backed distribution path
non-configurably unavailable. At that time there was no concrete repository or
ownership model, and the old downloader and extraction path had not received the
security work required to install remotely supplied code.

There is now a concrete operating model. Sheet Delver modules are maintained in
independent public repositories and released as packaged artifacts. Operators
need a low-overhead way to discover, install, and update those modules without
copying archives into the data directory manually. They must also be able to
install a public module that is not yet present in the curated catalog.

A separately operated package service is unnecessary for this stage. A static
catalog hosted by GitHub Pages can provide discovery, while each module
repository remains responsible for its own releases. Static hosting also keeps
the catalog inspectable, cacheable, inexpensive, and independent of a running
Sheet Delver instance.

Remote modules execute trusted application code. Convenience cannot bypass the
security and lifecycle boundaries already established for managed modules.

## Decision

Sheet Delver will support public, manifest-driven module distribution. The
official discovery catalog will be a versioned static JSON document hosted with
GitHub Pages. Catalog entries point to release manifests owned by public module
repositories. Release manifests point to immutable packaged archives.

All acquisition methods converge on the existing managed-module installation
boundary. This ADR does not create a third runtime module mode.

### 1. Distribution has three documents with separate responsibilities

#### Runtime module manifest

`info.json` remains the authoritative manifest inside an installed module. It
defines runtime entry points, compatibility contracts, permissions, package
content, and module metadata as documented in `docs/MODULE_MANIFEST.md`.

#### Release manifest

Each published module release includes a generated
`sheet-delver-manifest.json`. It contains the metadata needed to evaluate a
release before downloading or activating it:

- release-manifest schema version
- module id, title, and version
- public repository and changelog URLs when available
- immutable HTTPS artifact URL or sibling release-asset name that resolves
  against the final version-specific release-manifest URL
- artifact byte size and SHA-256 digest
- core and SDK contract compatibility copied from `info.json`
- permission, dependency, and conflict declarations copied from `info.json`
- publication timestamp

The release manifest is generated by the module packaging workflow. Authors do
not maintain duplicated compatibility or permission declarations by hand. An
installation fails if the downloaded archive's `info.json` does not match the
release manifest's module id, version, compatibility, or permission metadata.

New module scaffolds include separate validation and tag-triggered release
workflows. Both workflows pin an explicit Sheet Delver core ref. The initializer
defaults that ref from the root application version and permits an explicit
override for testing a pushed development ref; published module workflows use a
tested Sheet Delver release tag.

#### Static catalog index

The GitHub Pages index is a discovery document, not a second release database.
Each entry contains only catalog metadata such as:

- module id and title
- public repository URL
- stable public release-manifest URL
- catalog classification and optional descriptive metadata

Release versions, artifact digests, permissions, and compatibility constraints
are not copied into the index. This avoids three manually maintained versions of
the same release facts.

The first implementation resolves the current release exposed by the stable
manifest URL. Installed artifacts retain enough local history for rollback.
Historical remote version browsing can be introduced through a later schema
revision without changing the installation boundary.

### 2. Supported acquisition methods are public and explicit

The manager will support these inputs:

1. A module selected from an enabled static catalog.
2. A direct public HTTPS URL to `sheet-delver-manifest.json`.
3. A public GitHub repository shortcut resolved to that repository's conventional
   GitHub Release manifest asset.
4. An operator-supplied local `.tgz` archive.

A GitHub repository shortcut is resolution convenience only. Sheet Delver will
not clone repositories, run package-manager install hooks, compile source, or
execute publisher build scripts on the host. Production installation consumes
only a prebuilt archive.

Private repositories, authenticated indexes, bearer tokens, deploy keys, and
distribution credential storage are not supported. Existing authentication
fields in dormant source-profile scaffolding do not become part of this
capability and must not appear in the active UI.

### 3. Catalog inclusion and release metadata do not self-assign trust

Trust is derived from local source policy:

- the built-in official catalog may assign the configured catalog trust
  classification to an entry
- an operator-added catalog is classified as `unverified`
- a direct manifest or repository shortcut is unverified unless local policy
  explicitly recognizes its source
- a release manifest cannot promote itself to `first-party` or
  `verified-third-party`

SHA-256 verifies that the downloaded bytes match the selected release manifest.
It does not independently prove publisher identity. HTTPS, the configured source
identity, catalog curation, and explicit operator action form the initial source
trust model. Cryptographic publisher signing may be added by a separate ADR if
the operating model later requires it.

### 4. Network access is HTTPS-only and fail-closed

Remote distribution is available only through the dedicated distribution HTTP
client. The client must enforce all of the following for the initial request and
every redirect:

- HTTPS scheme
- configured hostname allowlist
- DNS and destination-address rejection for loopback, private, link-local,
  multicast, unspecified, and other non-public ranges
- bounded redirects, connect timeout, response timeout, and retries
- response content-type checks where meaningful
- compressed download-size and decompressed archive-size limits
- release-manifest and catalog JSON size limits
- no cookies, ambient credentials, or authorization headers

Host governance remains fail-closed in development and production. Development
does not gain a bypass for arbitrary remote hosts. Local development uses
`local://`, `file://`, or an operator-supplied archive instead.

The official catalog and the public hosts required by its GitHub Pages and
GitHub Release URLs may be configured as defaults. Additional public hosts
require an explicit admin source configuration before use.

### 5. Archive installation is staged, validated, and atomic

An archive is never extracted directly into `<DATA_DIR>/modules`.
`<DATA_DIR>/local/modules` is outside the distribution subsystem's write
boundary: remote fetches, archive uploads, installs, upgrades, rollbacks, and
uninstalls must never create, replace, rename, or delete content there.

The installer will:

1. Write the downloaded or uploaded archive to an isolated staging area.
2. Verify its expected byte size and SHA-256 digest when a release manifest is
   present.
3. Inspect archive entries before extraction.
4. Reject absolute paths, traversal, symlinks, hard links, device entries,
   excessive file counts, excessive path lengths, and size-limit violations.
5. Extract into a newly created staging directory.
6. Require exactly one valid module root with `info.json`.
7. Run the existing packaged-module health, SDK contract, core compatibility,
   dependency/conflict, trust, and permission gates.
8. Confirm release-manifest and archive-manifest identity.
9. Preserve the currently installed artifact as rollback material.
10. Atomically promote the validated staging directory to
    `<DATA_DIR>/modules/<moduleId>` and update lifecycle/artifact state.

Any failure before promotion leaves the active installation unchanged. A failure
after promotion triggers deterministic rollback or records a blocked state that
requires operator action; it must not silently leave a partial module tree.

Local archive installation uses the same inspection, validation, promotion, and
rollback transaction. Digest input is optional for an explicitly uploaded local
archive, but its computed digest is always recorded.

If the same module id exists in both `local/modules` and `modules`, the managed
installation remains physically separate. The dry run must report the duplicate
source, installation must preserve the development tree byte-for-byte, and the
operation must not silently change the active source away from the developer's
current selection.

### 6. Install and activation remain separate operations

Installing or upgrading a package does not silently enable it for a world.
Existing lifecycle state and source selection continue to control activation.

The admin receives a dry-run summary before mutation containing:

- resolved source and release identity
- compatibility result
- trust classification
- digest verification expectation
- requested permissions and permission changes
- dependencies and conflicts
- install, upgrade, downgrade, or no-op outcome

Permission escalation continues to require explicit approval. Locking continues
to prevent update and uninstall. A failed or incompatible update leaves the
currently installed version available.

### 7. The official catalog is independently maintained

The official static index will live in a dedicated repository and be published
through GitHub Pages. It is version controlled and validated in CI before Pages
deployment.

Catalog changes do not require a Sheet Delver core release. Module releases do
not require an index change when their stable release-manifest URL is unchanged.
Adding another module consists of adding its public repository and stable
manifest pointer to the catalog.

The client validates the catalog schema and treats duplicate module ids across
enabled catalogs as an explicit conflict. Source priority must never silently
replace an installed module with a same-id package from another source.

### 8. Remote activation replaces ADR-0033's blanket denial only when complete

ADR-0033's `remote-module-distribution-disabled` behavior remains in force while
this ADR is proposed or only partially implemented. It is removed only after the
network client, release-manifest validation, secure archive transaction,
governance integration, tests, and operator documentation are complete.

There is no intermediate configuration switch that re-enables the old dormant
fetch or extraction scaffolding. The accepted implementation replaces that path
with the bounded capability defined here.

## Scope

### In scope

- generated release manifests and packaging workflow support
- local archive install, upgrade, and rollback
- public HTTPS release-manifest and artifact retrieval
- a GitHub Pages static catalog and catalog schema
- public GitHub repository shortcut resolution
- source-host administration without credentials
- admin discovery, dry-run, install, update, lock, rollback, and uninstall flows
- migration of existing official modules to the release workflow
- tests and operator/module-author documentation

### Out of scope

- private repositories or authenticated distribution
- bearer tokens, deploy keys, or distribution credential storage
- repository cloning or host-side module builds
- public marketplace submissions, ratings, reviews, or publisher accounts
- automatic dependency installation
- cryptographic publisher key infrastructure
- runtime sandboxing of installed module code
- historical remote version catalogs in the initial schema
- a standalone module-author CLI independent of a Sheet Delver core checkout

## Implementation Plan

### Phase 1: Contracts and release tooling

- define and test the release-manifest and catalog schemas
- extend `module:package` to emit the archive, release manifest, and digest
- add a reusable public-module release workflow
- generate pinned module validation and release callers from `module:init`
- document the conventional GitHub Release asset names and stable manifest URL

**Exit:** A module repository can publish an immutable archive and generated,
schema-valid release manifest without core installation support.

### Phase 2: Secure local archive transaction

- implement bounded tar inspection and extraction
- stage and validate packaged modules through existing governance gates
- atomically install, upgrade, and roll back managed module directories
- expose CLI and admin upload/dry-run operations

**Exit:** An operator can safely install the same release archive locally, and
failed validation or promotion cannot damage the active module.

### Phase 3: Public distribution client

- replace the dormant generic fetcher with a dedicated fail-closed client
- implement URL, redirect, DNS/address, timeout, retry, and size policy
- fetch and validate public release manifests and artifacts
- enable direct manifest and public GitHub repository resolution

**Exit:** A configured public release can be dry-run and installed without any
path around the local archive transaction.

### Phase 4: Static catalog and source integration

- create the dedicated catalog repository and GitHub Pages deployment
- revise the existing index model to catalog release-manifest pointers
- add the official catalog source and credential-free custom public sources
- handle refresh caching, duplicate ids, source priority, pinning, and locking

**Exit:** Admin discovery and updates work from the official static catalog, and
catalog changes do not require a core release.

### Phase 5: Admin UX, migration, and closeout

- provide Available, Installed, Updates, and Sources views
- show dry-run security and compatibility results before mutation
- publish existing official modules with the new release assets
- update configuration, security, authoring, manifest, API, and release docs
- run unit, integration, adversarial archive, controlled HTTP, rollback,
  restart, and live installation acceptance tests

**Exit:** The blanket remote-distribution denial is replaced only for the public
paths in this ADR, official modules install and update through the catalog, and
local and managed runtime behavior remains unchanged.

## Closeout (September 22, 2026)

This status correction records the already-shipped decision; it introduces no
new distribution capability. Implementation merged in `eeec4df` (PR #14), with
runtime restart and historical selection subsequently covered by ADR-0036 and
ADR-0037. The user confirmed catalog installs/updates, uninstall/reinstall with
disabled state preserved, source switching, maintenance recovery and production
managed-module use during the subsequent release work.

The full unit and local integration suites passed again on September 22. The
archive tests exercise traversal/link/duplicate rejection, staging, promotion,
rollback and preservation of local developer content. Public distribution tests
exercise host/address/redirect policy, bounded responses, retry, digest checks,
manifest selection and archive installation with injected DNS/request-hop
fixtures. These are controlled transport tests, not live adversarial network
tests or a fresh production deployment. Policy tests cover locks, pins and
permission approval independently of the operator smoke confirmations.

The manifest-driven public path is active. Legacy raw remote-source scaffolding
remains denied intentionally; its `remote-module-distribution-disabled` errors
are not an unfinished activation task. The original phase checklist is historical
and should not be recreated as release work. Deferred capabilities below and
under Out of scope require a separately approved use case.

## Tentative Follow-up

Consider a standalone module-author CLI if requiring a core checkout becomes a
meaningful source of friction. Module repositories are already operationally
self-contained in CI: their generated workflows invoke validation, packaging,
and release from the module repository while checking out a pinned core
toolchain. The tentative CLI would provide the same local experience without a
full core checkout.

Any such CLI must remain a thin distribution of the authoritative core schemas
and module tooling. It must not introduce a second implementation of manifest
validation, packaging, or release generation that can drift from the host. It
is not required to complete this ADR.

## Consequences

### Positive

- end users can discover and install modules without manual server file work
- module repositories retain independent release cadence and ownership
- static hosting avoids a new production service
- generated metadata minimizes maintenance drift
- every install path uses one hardened managed-module transaction
- core releases are decoupled from catalog and module releases

### Costs and tradeoffs

- remote code distribution increases supply-chain and network attack surface
- module packaging and release workflows become stricter
- GitHub Pages and GitHub Releases are initial infrastructure dependencies
- latest-only discovery does not initially provide a complete remote version
  browser
- SHA-256 and curated HTTPS sources are weaker identity guarantees than a
  publisher-signing infrastructure

## Alternatives Considered

### Operate a dedicated package service

Deferred. It adds deployment, availability, authentication, and maintenance
cost without current functionality that cannot be supplied by versioned static
documents.

### Store complete release metadata in the static index

Rejected. It duplicates release facts from module repositories and creates an
additional update requirement for every module release.

### Install directly from a repository branch

Rejected. Branches are mutable and would require cloning, dependency
installation, and untrusted build execution on the Sheet Delver host.

### Support private repositories

Rejected for this operating model. Credential setup, token scopes, rotation,
secret persistence, and provider-specific failure handling add substantial
operator overhead. Public releases and local archive installation cover the
required workflows.

### Trust release-manifest declarations directly

Rejected. A package cannot assign its own trust tier. Trust remains a local
policy decision derived from the configured source.
